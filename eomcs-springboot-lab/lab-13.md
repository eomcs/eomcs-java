# 13장. 사용자 인증 구현

12장에서는 Spring Security의 처리 구조를 배우고, 설정 파일에 적은 **사용자 한 명**(`spring.security.user.*`)으로 로그인했다.
이번 장에서는 사용자를 **데이터베이스**에 저장하고, 그 사용자로 로그인하도록 인증 과정을 직접 구현한다.
사용자 **엔티티와 리포지토리**를 만들고, Spring Security에 사용자 정보를 알려 주는 `UserDetailsService`와 비밀번호를 안전하게 저장하는 `PasswordEncoder`를 배운다.
그리고 **회원가입** 화면과 **로그인·로그아웃** 화면을 직접 만들고, 게시글의 작성자를 로그인한 사용자로 정한다.

## 인증 과정 살펴보기

### 12장과 무엇이 달라지는가

| 구분 | 12장 | 13장 |
| --- | --- | --- |
| 사용자 정보 | `application.properties`의 한 명 | 데이터베이스의 `users` 테이블 (여러 명) |
| 사용자 등록 | 설정 파일을 고친다. | **회원가입** 화면에서 등록한다. |
| 비밀번호 저장 | 설정 파일에 그대로(`1234`) | **암호화**하여 저장한다. (`PasswordEncoder`) |
| 로그인 화면 | Spring Security가 만든 기본 화면 | 직접 만든 화면 |
| 게시글 작성자 | 폼에 직접 입력 | **로그인한 사용자**의 아이디 |

### 아이디와 비밀번호를 확인하는 과정

12장에서 로그인 요청(`POST /login`)은 `UsernamePasswordAuthenticationFilter`가 처리한다고 배웠다. 이 필터는 아이디와 비밀번호를 직접 확인하지 않고, 다음 객체들에 일을 맡긴다.

```
POST /login (username, password)
 │
 ▼
UsernamePasswordAuthenticationFilter
 └─ AuthenticationManager                       ← 인증을 총괄한다.
     └─ DaoAuthenticationProvider               ← 아이디·비밀번호 방식의 인증을 처리한다.
         ├─ UserDetailsService                  ← (1) 아이디로 사용자 정보를 찾는다.  [직접 구현]
         │   └─ UserRepository → users 테이블
         └─ PasswordEncoder                     ← (2) 비밀번호를 비교한다.           [빈 등록]
```

| 순서 | 처리 | 담당 |
| --- | --- | --- |
| 1 | 입력한 아이디로 사용자 정보(아이디, 암호화된 비밀번호, 권한)를 찾는다. 없으면 인증 실패 | `UserDetailsService` |
| 2 | 입력한 비밀번호와 저장된 비밀번호가 맞는지 비교한다. 틀리면 인증 실패 | `PasswordEncoder` |
| 3 | 성공하면 `Authentication` 객체를 만들어 `SecurityContextHolder`와 세션에 저장한다. (12장) | Spring Security |

Spring Security는 사용자 정보가 **어디에 어떤 형태로** 저장되어 있는지 모른다. 그래서 개발자가 `UserDetailsService`를 구현하여 "아이디로 사용자를 찾는 방법"을 알려 준다.
나머지 과정(비밀번호 비교, 인증 결과 저장, 세션 관리)은 Spring Security가 처리한다.

## 사용자 테이블과 엔티티

### 사용자 테이블

6장에서 정한 대로 테이블은 **DDL 스크립트**(`db/schema.sql`)로 정의한다.

```sql
-- 사용자 테이블 (13장)
CREATE TABLE IF NOT EXISTS users (
  id       BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,  -- 사용자 번호 (자동 증가)
  username VARCHAR(20)  NOT NULL UNIQUE,                               -- 로그인 아이디 (중복 불가)
  password VARCHAR(100) NOT NULL,                                      -- 암호화된 비밀번호
  role     VARCHAR(20)  NOT NULL DEFAULT 'USER'                        -- 역할 (USER, ADMIN)
);
```

| 열 | 설명 |
| --- | --- |
| `username` | 로그인 아이디. `UNIQUE` 제약 조건으로 같은 아이디가 두 번 저장되지 않게 한다. |
| `password` | 비밀번호를 **암호화한 값**을 저장한다. 암호화한 값은 원래 비밀번호보다 길기 때문에(68자) 넉넉하게 `VARCHAR(100)`으로 정한다. |
| `role` | 사용자의 역할. 값을 지정하지 않으면 `USER`가 저장된다. 관리자(`ADMIN`)는 14장에서 사용한다. |

> 테이블 이름을 `user`로 하지 않는 이유: `USER`는 H2를 비롯한 여러 데이터베이스에서 **예약어**(SQL 문법에 쓰이는 단어)이므로 테이블 이름으로 쓰면 오류가 나거나 따옴표로 감싸야 한다. 그래서 `users`로 정한다.

### 사용자 엔티티와 리포지토리

사용자 관련 클래스는 새 패키지 `com.example.hello.user`에 둔다.
엔티티의 이름은 `UserEntity`로 한다. Spring Security에 `User`라는 클래스가 이미 있으므로 이름이 겹치지 않게 한다.

```java
@Entity
@Table(name = "users")
public class UserEntity {

  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  private String username;     // 로그인 아이디
  private String password;     // 암호화된 비밀번호
  private String role;         // 역할

  ...
}
```

리포지토리에는 아이디로 사용자를 찾는 **쿼리 메서드**(7장)를 추가한다.

```java
public interface UserRepository extends JpaRepository<UserEntity, Long> {

  Optional<UserEntity> findByUsername(String username);   // SELECT ... WHERE username = ?

  boolean existsByUsername(String username);              // 같은 아이디가 있는지 확인
}
```

| 메서드 | 사용하는 곳 |
| --- | --- |
| `findByUsername()` | 로그인할 때 아이디로 사용자를 찾는다. (`UserDetailsService`) |
| `existsByUsername()` | 회원가입할 때 이미 사용 중인 아이디인지 확인한다. |

## 비밀번호 저장: PasswordEncoder

### 비밀번호를 그대로 저장하면

비밀번호를 입력한 그대로(**평문**) 저장하면, 데이터베이스가 유출되었을 때 모든 사용자의 비밀번호가 그대로 드러난다.
많은 사람이 여러 사이트에 같은 비밀번호를 사용하므로, 한 사이트의 유출이 다른 사이트의 피해로 이어진다. 데이터베이스를 관리하는 **내부 직원**도 비밀번호를 볼 수 있어서는 안 된다.

그래서 비밀번호는 **되돌릴 수 없는 값**으로 바꾸어 저장한다.

| 방식 | 설명 | 비밀번호 저장에 |
| --- | --- | --- |
| 평문 | 그대로 저장 | 사용하면 안 된다. |
| 암호화 (양방향) | 열쇠(key)가 있으면 원래 값으로 되돌릴 수 있다. | 열쇠가 유출되면 모두 드러나므로 적합하지 않다. |
| **해시** (단방향) | 원래 값으로 되돌릴 수 없다. 같은 입력은 항상 같은 결과가 나온다. | 적합하다. (단, 다음의 보완이 필요하다.) |

로그인할 때는 입력한 비밀번호를 **같은 방법으로 해시하여** 저장된 값과 비교한다. 원래 비밀번호를 알 필요가 없다.

> 이 교재에서는 흔히 쓰는 말대로 "비밀번호 암호화"라고 부르지만, 정확히는 **단방향 해시**이다.

### 솔트와 BCrypt

단순한 해시는 같은 비밀번호가 항상 같은 값이 되므로, 자주 쓰는 비밀번호의 해시 값을 미리 계산해 둔 표(레인보우 테이블)로 쉽게 알아낼 수 있다.
이를 막기 위해 비밀번호마다 **솔트**(salt)라는 임의의 값을 섞어 해시한다. 그러면 **같은 비밀번호라도 저장되는 값이 모두 다르다.**

Spring Security가 기본으로 사용하는 **BCrypt**는 다음 특징이 있다.

- 비밀번호마다 솔트를 자동으로 만들어 섞고, 솔트를 결과 값 안에 함께 저장한다.
- 해시를 여러 번 반복하여 **일부러 느리게** 계산한다. 공격자가 비밀번호를 하나씩 대입해 보는 속도를 늦춘다.

BCrypt로 해시한 값은 다음과 같은 60자의 문자열이다.

```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
```

| 부분 | 값 | 의미 |
| --- | --- | --- |
| 버전 | `$2a$` | BCrypt 알고리즘의 버전 |
| 비용 | `10$` | 반복 횟수. 2의 10제곱(1024)번 반복한다. 값이 1 커질 때마다 계산 시간이 2배가 된다. |
| 솔트 | 다음 22자 | 이 비밀번호에 사용한 임의의 솔트 |
| 해시 | 나머지 31자 | 솔트와 비밀번호로 계산한 해시 값 |

### PasswordEncoder

Spring Security는 비밀번호 해시를 `PasswordEncoder` 인터페이스로 다룬다.

| 메서드 | 기능 |
| --- | --- |
| `encode(비밀번호)` | 비밀번호를 해시한다. 회원가입할 때 사용한다. |
| `matches(입력한 비밀번호, 저장된 값)` | 입력한 비밀번호가 저장된 값과 맞는지 확인한다. 로그인할 때 Spring Security가 사용한다. |

> 되돌리는 메서드(`decode`)는 **없다.** 저장된 값을 비교할 때는 `encode()` 결과를 `equals()`로 비교하면 안 된다. 솔트 때문에 `encode()`할 때마다 결과가 다르므로 항상 `matches()`를 사용한다.

`PasswordEncoder`는 다음과 같이 **빈으로 등록**한다.

```java
@Bean
public PasswordEncoder passwordEncoder() {
  return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}
```

`createDelegatingPasswordEncoder()`가 만드는 `DelegatingPasswordEncoder`는 해시한 값 앞에 **어떤 방식으로 해시했는지** 표시한다.

```
{bcrypt}$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
```

| 저장된 값 | 비교 방법 |
| --- | --- |
| `{bcrypt}...` | BCrypt로 비교한다. (새로 저장하는 값은 모두 이 방식) |
| `{noop}...` | 해시하지 않은 **평문**으로 비교한다. (12장의 `spring.security.user.password`는 내부적으로 이 방식으로 저장되었다.) |
| `{argon2}...`, `{pbkdf2}...` 등 | 해당 방식으로 비교한다. |

나중에 더 안전한 방식이 나와 기본 방식을 바꾸더라도, 이미 저장된 비밀번호는 앞의 표시(`{bcrypt}`)를 보고 원래 방식으로 비교할 수 있다. 그래서 `new BCryptPasswordEncoder()`를 직접 사용하는 것보다 이 방법이 권장된다.

## UserDetailsService

### 사용자 정보를 알려 주는 인터페이스

`UserDetailsService`는 메서드가 하나뿐인 인터페이스이다.

```java
public interface UserDetailsService {
  UserDetails loadUserByUsername(String username) throws UsernameNotFoundException;
}
```

- 아이디(`username`)를 받아 사용자 정보(`UserDetails`)를 리턴한다.
- 사용자가 없으면 `UsernameNotFoundException` 예외를 던진다.

`UserDetails`는 Spring Security가 이해하는 **사용자 정보의 형식**이다.

| 메서드 | 의미 |
| --- | --- |
| `getUsername()` | 아이디 |
| `getPassword()` | 저장된(해시한) 비밀번호. `PasswordEncoder`가 입력한 비밀번호와 비교한다. |
| `getAuthorities()` | 권한 목록 (예: `ROLE_USER`) |
| `isEnabled()`, `isAccountNonLocked()` 등 | 계정 사용 가능 여부, 잠김 여부 등. 기본값은 모두 `true` |

`UserDetails`는 Spring Security가 제공하는 `User` 클래스로 쉽게 만들 수 있다.

```java
@Service
public class LoginUserDetailsService implements UserDetailsService {
  ...
  @Override
  public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
    UserEntity user = userRepository.findByUsername(username)
        .orElseThrow(() -> new UsernameNotFoundException("사용자를 찾을 수 없습니다: " + username));

    return User.withUsername(user.getUsername())   // 엔티티 → UserDetails
        .password(user.getPassword())
        .roles(user.getRole())                     // "USER" → 권한 "ROLE_USER"
        .build();
  }
}
```

이 클래스를 **빈으로 등록**하기만 하면, Spring Security가 찾아서 로그인할 때 사용한다. 12장의 `spring.security.user.*` 설정으로 만들던 사용자는 더 이상 만들어지지 않는다.

> 엔티티(`UserEntity`)를 Spring Security에 그대로 넘기지 않고 `UserDetails`로 바꾸어 넘긴다. 8장에서 엔티티를 API 응답에 그대로 쓰지 않고 DTO로 바꾼 것과 같은 이유이다. 보안 계층은 필요한 정보(아이디, 비밀번호, 권한)만 알면 된다.

### 아이디가 없을 때와 비밀번호가 틀렸을 때

없는 아이디로 로그인하면 `UsernameNotFoundException`, 비밀번호가 틀리면 `BadCredentialsException`이 발생한다.
그런데 Spring Security는 두 경우를 **구별하지 않고** 똑같이 "인증 실패"로 처리한다.

"없는 아이디입니다"와 "비밀번호가 틀렸습니다"를 구별해서 알려 주면, 공격자가 어떤 아이디가 가입되어 있는지 알아낼 수 있기 때문이다.
로그인 화면의 오류 메시지도 "**아이디 또는 비밀번호**가 올바르지 않습니다"처럼 구별하지 않고 표시한다.

## 회원가입

### 회원가입 처리 과정

회원가입은 11장의 등록 폼과 같은 방식(폼 객체, 검증, PRG 패턴)으로 만든다.

| 순서 | 처리 | 담당 |
| --- | --- | --- |
| 1 | `GET /signup`: 빈 회원가입 폼을 보여 준다. | 컨트롤러 |
| 2 | `POST /signup`: 입력 값을 검증한다. (아이디 형식, 비밀번호 길이, 비밀번호 확인) | 컨트롤러 (`@Valid`) |
| 3 | 이미 사용 중인 아이디인지 확인한다. | 서비스 |
| 4 | 비밀번호를 **해시**하여 사용자를 저장한다. | 서비스 (`PasswordEncoder`) |
| 5 | 로그인 화면으로 **리다이렉트**하고 "회원가입을 완료했습니다" 메시지를 보여 준다. | 컨트롤러 |

| 주소 | 메서드 | 기능 | 접근 |
| --- | --- | --- | --- |
| `/signup` | `GET` | 회원가입 폼 | 누구나 |
| `/signup` | `POST` | 회원가입 처리 | 누구나 |
| `/login` | `GET` | 로그인 화면 (직접 만든 화면) | 누구나 |
| `/login` | `POST` | 로그인 처리 (**Spring Security**가 처리) | 누구나 |
| `/logout` | `POST` | 로그아웃 처리 (**Spring Security**가 처리) | |

로그인과 로그아웃 **처리**는 Spring Security의 필터가 하므로 컨트롤러를 만들지 않는다. 컨트롤러는 로그인 **화면**(`GET /login`)만 보여 준다.

### 입력 값 검증

회원가입 폼 객체(`SignupForm`)에는 11장에서 배운 검증 애노테이션과 함께 다음 애노테이션을 사용한다.

| 애노테이션 | 검사 내용 |
| --- | --- |
| `@Pattern(regexp = "정규 표현식")` | 문자열이 정규 표현식과 맞는지 검사한다. `null`은 검사하지 않는다. |
| `@NotNull` | `null`이 아니어야 한다. (빈 문자열 `""`은 통과) |

```java
@NotNull(message = "아이디를 입력하세요.")
@Pattern(regexp = "^[a-z0-9]{4,20}$", message = "아이디는 영문 소문자와 숫자 4~20자로 입력하세요.")
private String username;
```

- `^[a-z0-9]{4,20}$`: 처음(`^`)부터 끝(`$`)까지 영문 소문자와 숫자(`[a-z0-9]`)가 4~20개(`{4,20}`)
- 아무것도 입력하지 않으면 `""`이 전달되어 `@Pattern` 검사에서 걸린다. `@NotBlank`를 함께 쓰면 오류 메시지가 두 개 표시되므로 `@NotNull`을 사용한다.

**비밀번호 확인**처럼 두 항목을 비교하는 검사는 컨트롤러에서 직접 하고, `BindingResult`에 오류를 추가한다.

```java
if (!Objects.equals(form.getPassword(), form.getPasswordConfirm())) {
  bindingResult.rejectValue("passwordConfirm", "mismatch", "비밀번호가 일치하지 않습니다.");
}
```

`rejectValue(항목 이름, 오류 코드, 기본 메시지)`로 추가한 오류는 애노테이션의 검증 오류와 똑같이 템플릿의 `data-th-errors`로 출력된다.

### 아이디 중복 확인

같은 아이디로 두 번 가입할 수 없어야 한다. 서비스에서 저장하기 전에 `existsByUsername()`으로 확인하고, 이미 있으면 **예외**를 던진다. 컨트롤러는 예외를 받아 아이디 항목에 오류를 추가한다.

> 두 사람이 **동시에** 같은 아이디로 가입하면, 두 요청 모두 "없는 아이디"로 확인된 후 저장될 수 있다. 이 경우에는 테이블의 `UNIQUE` 제약 조건이 두 번째 저장을 막는다. 애플리케이션의 검사와 데이터베이스의 제약 조건을 **함께** 사용하는 이유이다.

## 로그인·로그아웃 화면 직접 만들기

### 로그인 화면 지정하기

로그인 화면을 직접 만들려면 `formLogin()`에 로그인 화면의 주소를 지정한다.

```java
.formLogin(form -> form
    .loginPage("/login")                  // 로그인 화면 주소 (GET /login은 컨트롤러가 처리)
    .defaultSuccessUrl("/web/boards")
    .permitAll())                         // 로그인 화면과 로그인 처리 주소를 누구나 접근하게 한다.
```

`loginPage()`를 지정하면 Spring Security의 **기본 로그인 화면과 기본 로그아웃 화면이 만들어지지 않는다.**

### 로그인 폼의 규칙

직접 만든 로그인 폼은 Spring Security가 처리할 수 있도록 다음 규칙을 지켜야 한다.

| 항목 | 규칙 |
| --- | --- |
| 폼을 보낼 주소 | `POST /login` (`loginPage()`로 지정한 주소와 같다.) |
| 아이디 입력 항목 이름 | `username` |
| 비밀번호 입력 항목 이름 | `password` |
| CSRF 토큰 | 필요하다. `data-th-action`을 사용하면 자동으로 추가된다. |

로그인 결과에 따라 Spring Security가 다음 주소로 리다이렉트한다. 템플릿에서는 `${param.이름}`으로 요청 파라미터가 있는지 확인하여 메시지를 보여 준다.

| 결과 | 리다이렉트 주소 | 템플릿에서 확인 |
| --- | --- | --- |
| 로그인 성공 | 로그인 전에 요청했던 주소, 없으면 `/web/boards` | |
| 로그인 실패 | `/login?error` | `data-th-if="${param.error}"` |
| 로그아웃 | `/login?logout` | `data-th-if="${param.logout}"` |

### 로그아웃은 POST로

12장에서는 `GET /logout`으로 접속하면 Spring Security가 만든 "로그아웃할지 묻는 화면"이 나왔다. 로그인 화면을 직접 만들면 이 화면도 없어지므로, 로그아웃 버튼을 **`POST` 폼**으로 만든다.

```html
<form method="post" action="#" data-th-action="@{/logout}">
  <button type="submit">로그아웃</button>
</form>
```

로그아웃이 `GET`이 아니라 `POST`인 이유는 **CSRF** 때문이다. `GET`으로 로그아웃할 수 있으면, 다른 사이트의 이미지 태그(`<img src="http://localhost:8080/logout">`)만으로도 사용자를 몰래 로그아웃시킬 수 있다.

로그아웃하면 Spring Security가 다음을 처리한다.

- 세션을 없앤다. (세션에 저장된 인증 정보도 함께 없어진다.)
- `SecurityContextHolder`의 인증 정보를 지운다.
- `/login?logout`으로 리다이렉트한다.

### 세션 고정 공격 방어

로그인에 성공하면 Spring Security는 **세션 ID를 새로 바꾼다.**

공격자가 자신이 받은 세션 ID를 어떤 방법으로 다른 사람의 웹 브라우저에 심어 두고(세션 고정), 그 사람이 로그인하기를 기다린다고 하자.
로그인한 후에도 세션 ID가 그대로라면, 공격자는 자신이 알고 있는 세션 ID로 그 사람의 계정을 사용할 수 있다.
로그인할 때 세션 ID를 바꾸면 공격자가 알고 있던 세션 ID는 쓸모없어진다. 실습-5에서 `JSESSIONID`가 바뀌는 것을 확인한다.

## 로그인한 사용자 정보 사용하기

### @AuthenticationPrincipal

컨트롤러에서 로그인한 사용자의 정보가 필요하면, 파라미터에 `@AuthenticationPrincipal`을 붙인다.

```java
@PostMapping
public String create(..., @AuthenticationPrincipal UserDetails loginUser, ...) {
  String username = loginUser.getUsername();     // 로그인한 사용자의 아이디
  ...
}
```

`@AuthenticationPrincipal`은 `SecurityContextHolder`에 보관된 `Authentication`의 **principal**(사용자 정보)을 꺼내 준다.
이 principal은 `UserDetailsService`가 리턴한 `UserDetails` 객체이다.

| 파라미터 | 받는 값 |
| --- | --- |
| `Authentication authentication` | 인증 정보 전체 (12장 `MeController`) |
| `@AuthenticationPrincipal UserDetails loginUser` | 인증 정보 중 사용자 정보(principal) |

### 작성자를 로그인한 사용자로

11장에서는 게시글의 작성자를 폼에 **직접 입력**했다. 누구나 다른 사람의 이름으로 글을 쓸 수 있었다.
이제 작성자 입력 항목을 없애고, **로그인한 사용자의 아이디**를 작성자로 저장한다. REST API의 게시글 등록도 요청 본문의 `writer` 대신 인증한 사용자의 아이디를 사용한다.

> 사용자가 보낸 값은 조작할 수 있다. 누가 요청했는지는 요청 본문이 아니라 **인증 정보**로 판단해야 한다.

지금은 로그인한 사용자라면 **누구의 게시글이든** 수정·삭제할 수 있다. 자신의 게시글만 수정·삭제하게 하고, 관리자는 모든 게시글을 삭제할 수 있게 하는 것은 14장에서 다룬다.

## 정리

| 주제 | 핵심 내용 |
| --- | --- |
| 인증 과정 | `AuthenticationManager` → `DaoAuthenticationProvider`가 `UserDetailsService`로 사용자를 찾고, `PasswordEncoder`로 비밀번호를 비교한다. |
| 사용자 엔티티 | 테이블은 DDL(`users`)로 정의하고, `UserEntity`와 `UserRepository`(`findByUsername`, `existsByUsername`)를 만든다. |
| PasswordEncoder | 비밀번호는 솔트를 섞은 단방향 해시(BCrypt)로 저장한다. `encode()`로 저장하고 `matches()`로 비교한다. `DelegatingPasswordEncoder`는 `{bcrypt}`처럼 방식을 표시한다. |
| UserDetailsService | `loadUserByUsername()`에서 엔티티를 찾아 `UserDetails`로 바꾸어 리턴한다. 빈으로 등록하면 Spring Security가 사용한다. |
| 회원가입 | 폼 객체 검증(`@Pattern`, `rejectValue`), 아이디 중복 확인(서비스 + `UNIQUE`), 비밀번호 해시 후 저장, 로그인 화면으로 리다이렉트 |
| 로그인·로그아웃 | `loginPage("/login")`으로 화면을 직접 만든다. 로그인·로그아웃 **처리**는 Spring Security가 한다. 로그아웃은 `POST`. 로그인하면 세션 ID가 바뀐다. |
| 로그인한 사용자 | `@AuthenticationPrincipal UserDetails`로 받는다. 작성자처럼 "누가"에 해당하는 값은 인증 정보로 정한다. |

### 실습-1: 사용자 테이블과 엔티티 만들기

**1) 테이블 정의하기**

`src/main/resources/db/schema.sql` 파일 아래에 다음 내용을 추가한다.

```sql
-- 사용자 테이블 (13장)
CREATE TABLE IF NOT EXISTS users (
  id       BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,  -- 사용자 번호 (자동 증가)
  username VARCHAR(20)  NOT NULL UNIQUE,                               -- 로그인 아이디 (중복 불가)
  password VARCHAR(100) NOT NULL,                                      -- 암호화된 비밀번호
  role     VARCHAR(20)  NOT NULL DEFAULT 'USER'                        -- 역할 (USER, ADMIN)
);
```

**2) 엔티티 만들기**

`com.example.hello` 패키지 아래에 `user` 패키지(폴더)를 만든다. 그 안에 `UserEntity.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.user;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "users")
public class UserEntity {

  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  private String username;     // 로그인 아이디

  private String password;     // 암호화된 비밀번호

  private String role;         // 역할 (USER, ADMIN)

  // JPA가 사용하는 기본 생성자
  protected UserEntity() {
  }

  // 새 사용자를 만들 때 사용하는 생성자
  public UserEntity(String username, String password, String role) {
    this.username = username;
    this.password = password;
    this.role = role;
  }

  public Long getId() {
    return id;
  }

  public String getUsername() {
    return username;
  }

  public String getPassword() {
    return password;
  }

  public String getRole() {
    return role;
  }

  @Override
  public String toString() {
    return "UserEntity[id=" + id + ", username=" + username + ", role=" + role + "]";   // 비밀번호는 출력하지 않는다.
  }
}
```

> `toString()`에 비밀번호를 넣지 않는다. 로그에 객체를 출력할 때 비밀번호(해시한 값이라도)가 남지 않게 하기 위해서이다.

**3) 리포지토리 만들기**

`user` 폴더에 `UserRepository.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.user;

import java.util.Optional;

import org.springframework.data.jpa.repository.JpaRepository;

public interface UserRepository extends JpaRepository<UserEntity, Long> {

  // 아이디로 사용자 찾기 (로그인)
  Optional<UserEntity> findByUsername(String username);

  // 같은 아이디가 있는지 확인 (회원가입)
  boolean existsByUsername(String username);
}
```

2. [http://localhost:8080/h2-console](http://localhost:8080/h2-console) 에 접속하여 `USERS` 테이블이 생긴 것을 확인한다.

### 실습-2: PasswordEncoder 사용하기

**1) PasswordEncoder 빈 등록하기**

`SecurityConfig.java`에 다음 메서드를 추가한다.

```java
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;

  // 비밀번호 해시 (기본: BCrypt)
  @Bean
  public PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
  }
```

> `PasswordEncoder` 빈을 등록하면 12장의 설정 사용자(`spring.security.user.*`)로는 로그인할 수 없다. 스프링 부트는 `PasswordEncoder` 빈이 없을 때만 설정의 비밀번호 앞에 `{noop}`을 붙여 주기 때문이다. 실습-3에서 사용자를 데이터베이스로 옮긴다.

**2) PasswordEncoder 동작 확인하기**

`src/test/java/com/example/hello` 폴더 아래에 `user` 폴더를 만들고, 그 안에 `PasswordEncoderTest.java` 파일을 만든다. 다음과 같이 작성한다.

```java
package com.example.hello.user;

import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertNotEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import org.junit.jupiter.api.Test;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;

class PasswordEncoderTest {

  // 스프링 컨테이너 없이 PasswordEncoder만 만들어 확인한다.
  private final PasswordEncoder passwordEncoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();

  @Test
  void encodeAndMatch() {
    String encoded1 = passwordEncoder.encode("1234");
    String encoded2 = passwordEncoder.encode("1234");
    System.out.println("encoded1 = " + encoded1);
    System.out.println("encoded2 = " + encoded2);

    assertNotEquals(encoded1, encoded2);                       // 같은 비밀번호라도 결과가 다르다. (솔트)
    assertTrue(passwordEncoder.matches("1234", encoded1));     // 비교는 matches()로 한다.
    assertTrue(passwordEncoder.matches("1234", encoded2));
    assertFalse(passwordEncoder.matches("12345", encoded1));   // 틀린 비밀번호
  }
}
```



`BUILD SUCCESSFUL`이 출력되면 테스트의 검사(`assert...`)를 모두 통과한 것이다.

테스트 결과 보고서(`build/reports/tests/test/index.html`)를 웹 브라우저로 연다. `PasswordEncoderTest` 클래스를 누르고 **Standard output** 탭을 선택하면 다음과 같은 출력이 보인다.

```

encoded2 = {bcrypt}$2a$10$7sLr1VbN0gQ5yT2eX8mZ3u8A9cD4fG6hJ1kL0pQ2rS5tU7vW9xY3z
```

- 두 값이 **다르다.** 비밀번호마다 다른 솔트를 사용하기 때문이다.
- 두 값 모두 `matches("1234", ...)`로 비교하면 `true`이다. 솔트가 값 안에 들어 있으므로 비교할 수 있다.
- 앞에 `{bcrypt}`가 붙어 있다. (`DelegatingPasswordEncoder`)

> 실제 출력되는 문자열은 실행할 때마다 다르다.

**`encoded1` 값을 복사해 둔다.** 실습-3에서 사용자를 데이터베이스에 직접 저장할 때 사용한다.

### 실습-3: UserDetailsService 구현하기

**1) 12장의 사용자 설정 지우기**

`application.properties`에서 12장에서 추가한 다음 설정을 **삭제**한다.

```properties
# 12장: 개발용 사용자 계정 (13장에서 데이터베이스의 사용자로 바꾼다.)
spring.security.user.name=user
spring.security.user.password=1234
spring.security.user.roles=USER
```

**2) UserDetailsService 구현하기**

`user` 폴더에 `LoginUserDetailsService.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.user;

import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.stereotype.Service;

// 로그인할 때 Spring Security가 호출하여 사용자 정보를 가져간다.
@Service
public class LoginUserDetailsService implements UserDetailsService {

  private final UserRepository userRepository;

  public LoginUserDetailsService(UserRepository userRepository) {
    this.userRepository = userRepository;
  }

  @Override
  public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
    UserEntity user = userRepository.findByUsername(username)
        .orElseThrow(() -> new UsernameNotFoundException("사용자를 찾을 수 없습니다: " + username));

    return User.withUsername(user.getUsername())   // 엔티티 → UserDetails
        .password(user.getPassword())              // 해시한 비밀번호 ({bcrypt}...)
        .roles(user.getRole())                     // "USER" → 권한 "ROLE_USER"
        .build();
  }
}
```

**3) 실행하고 확인하기**

애플리케이션을 다시 실행한다.

1. 실행 로그에 `Using generated security password`가 출력되지 않는다. 개발자가 `UserDetailsService`를 빈으로 등록했으므로 스프링 부트가 기본 사용자를 만들지 않는다.
2. 시크릿 창에서 [http://localhost:8080/web/boards/new](http://localhost:8080/web/boards/new) 에 접속하여 `user` / `1234`로 로그인한다. **로그인에 실패한다.** (`Bad credentials`) 아직 `users` 테이블에 사용자가 없다.

**4) 사용자를 직접 저장하기**

회원가입 화면은 실습-4에서 만든다. 여기서는 H2 콘솔에서 사용자를 직접 저장한다.
[http://localhost:8080/h2-console](http://localhost:8080/h2-console) 에서 다음 SQL을 실행한다. 비밀번호에는 **실습-2에서 복사한 값**을 붙여 넣는다.

```sql
INSERT INTO users (username, password)
VALUES ('user', '{bcrypt}$2a$10$Qk2u8xJ3v6pYk0cW1mX9QeJq0x7mH4nX2bT8wZ5rV3sY1uL9kP6aO');   -- 실습-2에서 복사한 값

SELECT * FROM users;
```

- `role`을 지정하지 않았으므로 기본값 `USER`가 저장된다.
- `password` 열에는 `1234`가 아니라 해시한 값이 저장되어 있다. 데이터베이스를 보는 사람도 비밀번호를 알 수 없다.

**5) 로그인하기**

다시 `user` / `1234`로 로그인한다. 이번에는 **로그인에 성공**한다.

1. 입력한 `user`로 `LoginUserDetailsService`가 `users` 테이블에서 사용자를 찾았다.
2. `PasswordEncoder`가 입력한 `1234`와 저장된 `{bcrypt}...` 값을 `matches()`로 비교했다.

[http://localhost:8080/me](http://localhost:8080/me) (12장 `MeController`)에 접속하면 `name`이 `user`, `authorities`에 `ROLE_USER`가 있는 것을 확인할 수 있다.

12장의 `http/security.http`도 아이디와 비밀번호(`user` / `1234`)가 같으므로 그대로 사용할 수 있다. 등록 요청(3번)을 보내 확인한다.

**6) (확인) 평문 비밀번호가 저장되어 있으면**

H2 콘솔에서 다음 SQL을 실행하여 비밀번호 앞에 `{noop}`을 붙인 사용자를 저장한다.

```sql
INSERT INTO users (username, password) VALUES ('noop', '{noop}1234');
```

`noop` / `1234`로 로그인한다. **로그인에 성공한다.** `{noop}`은 "해시하지 않은 평문"이라는 표시이므로 그대로 비교한다. 12장의 `spring.security.user.password=1234`도 이런 방식으로 처리되었다.

이번에는 표시 없이 평문만 저장한다.

```sql
INSERT INTO users (username, password) VALUES ('plain', '1234');
```

`plain` / `1234`로 로그인하면 **로그인에 실패**하고, 실행 로그에 다음과 비슷한 오류가 출력된다.

```
java.lang.IllegalArgumentException: Given that there is no default password encoder configured, each password must have a password encoding prefix. Please either prefix this password with '{noop}' or set a default password encoder in `DelegatingPasswordEncoder`.
```

"기본 비교 방법이 정해져 있지 않으므로, 모든 비밀번호 앞에 `{bcrypt}`, `{noop}` 같은 표시가 있어야 한다"는 뜻이다. `DelegatingPasswordEncoder`는 `{...}` 표시로 비교 방법을 정하는데, 표시가 없으니 비교할 방법을 찾지 못한 것이다.

확인한 후에는 두 사용자를 **삭제**한다. 평문 비밀번호는 실제로 사용하면 안 된다.

```sql
DELETE FROM users WHERE username IN ('noop', 'plain');
```

### 실습-4: 회원가입 구현하기

**1) 아이디 중복 예외 만들기**

`user` 폴더에 `DuplicateUsernameException.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.user;

// 이미 사용 중인 아이디로 가입하려고 할 때 발생하는 예외
public class DuplicateUsernameException extends RuntimeException {

  public DuplicateUsernameException(String username) {
    super("이미 사용 중인 아이디입니다: " + username);
  }
}
```

**2) 회원가입 서비스 만들기**

`user` 폴더에 `UserService.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.user;

import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@Transactional(readOnly = true)
public class UserService {

  private final UserRepository userRepository;
  private final PasswordEncoder passwordEncoder;     // 실습-2에서 등록한 빈

  public UserService(UserRepository userRepository, PasswordEncoder passwordEncoder) {
    this.userRepository = userRepository;
    this.passwordEncoder = passwordEncoder;
  }

  // 회원가입: 새 사용자의 번호를 리턴한다.
  @Transactional
  public Long signup(String username, String rawPassword) {
    if (userRepository.existsByUsername(username)) {
      throw new DuplicateUsernameException(username);                // 아이디 중복
    }
    String encodedPassword = passwordEncoder.encode(rawPassword);    // 비밀번호 해시
    UserEntity user = new UserEntity(username, encodedPassword, "USER");
    return userRepository.save(user).getId();
  }
}
```

> 비밀번호를 해시하는 일은 **서비스**가 맡는다. 컨트롤러나 리포지토리에서 해시하면, 해시하지 않고 저장하는 코드가 생기기 쉽다.

**3) 회원가입 폼 객체 만들기**

`user` 폴더에 `SignupForm.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.user;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;

// 회원가입 폼 객체
public class SignupForm {

  private String username;

  @NotNull(message = "비밀번호를 입력하세요.")
  @Size(min = 4, max = 50, message = "비밀번호는 4~50자로 입력하세요.")
  private String password;

  @NotBlank(message = "비밀번호 확인을 입력하세요.")
  private String passwordConfirm;

  public SignupForm() {
  }

  public String getUsername() {
    return username;
  }

  public void setUsername(String username) {
    this.username = username;
  }

  public String getPassword() {
    return password;
  }

  public void setPassword(String password) {
    this.password = password;
  }

  public String getPasswordConfirm() {
    return passwordConfirm;
  }

  public void setPasswordConfirm(String passwordConfirm) {
    this.passwordConfirm = passwordConfirm;
  }
}
```

> 실습을 편하게 하려고 비밀번호를 4자 이상으로 정했다. 실제 서비스에서는 8자 이상에 여러 종류의 문자를 섞도록 정하는 것이 좋다.

**4) 회원가입 컨트롤러 만들기**

`user` 폴더에 `UserWebController.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.user;

import java.util.Objects;

import jakarta.validation.Valid;

import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;

@Controller
public class UserWebController {

  private final UserService userService;

  public UserWebController(UserService userService) {
    this.userService = userService;
  }

  // 회원가입 폼: GET /signup
  @GetMapping("/signup")
  public String signupForm(Model model) {
    model.addAttribute("signupForm", new SignupForm());
    return "users/signup";
  }

  // 회원가입 처리: POST /signup
  @PostMapping("/signup")
  public String signup(@Valid @ModelAttribute("signupForm") SignupForm form,
                       BindingResult bindingResult,
                       RedirectAttributes redirectAttributes) {
    // 비밀번호 확인: 두 항목을 비교하는 검사는 직접 한다.
    if (!bindingResult.hasFieldErrors("passwordConfirm")
        && !Objects.equals(form.getPassword(), form.getPasswordConfirm())) {
      bindingResult.rejectValue("passwordConfirm", "mismatch", "비밀번호가 일치하지 않습니다.");
    }
    if (bindingResult.hasErrors()) {
      return "users/signup";
    }

    try {
      userService.signup(form.getUsername(), form.getPassword());
    } catch (DuplicateUsernameException e) {
      bindingResult.rejectValue("username", "duplicate", "이미 사용 중인 아이디입니다.");
      return "users/signup";
    }

    redirectAttributes.addFlashAttribute("message", "회원가입을 완료했습니다. 로그인하세요.");
    return "redirect:/login";                                // PRG: 로그인 화면으로
  }
}
```

지금까지 바꾼 `webFilterChain()` 전체는 다음과 같다. (`apiFilterChain()`과 `passwordEncoder()`는 생략)

```java
  // 2번 체인: 화면과 나머지 모든 요청
  @Bean
  @Order(2)
  public SecurityFilterChain webFilterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/css/**", "/error").permitAll()                              // 정적 자원, 오류 화면
            .requestMatchers("/swagger-ui.html", "/swagger-ui/**", "/v3/api-docs/**").permitAll()   // API 문서 (개발용)
            .requestMatchers("/h2-console/**").permitAll()                                 // H2 콘솔 (개발용)
            .requestMatchers("/signup").permitAll()                                        // 회원가입
            .requestMatchers("/hello/**", "/web/hello", "/web/greet", "/web/demo/**").permitAll()   // 연습용 주소
            .requestMatchers(HttpMethod.GET, "/web/boards/new").authenticated()            // 등록 폼 (다음 줄보다 먼저)
            .requestMatchers(HttpMethod.GET, "/web/boards", "/web/boards/{id}").permitAll() // 목록, 상세
            .anyRequest().authenticated())                                                 // 나머지는 로그인 필요
        .formLogin(form -> form
            .loginPage("/login")                                          // 직접 만든 로그인 화면
            .defaultSuccessUrl("/web/boards")                             // 로그인 후 이동할 기본 주소
            .permitAll())                                                 // 로그인 화면은 누구나
        .logout(Customizer.withDefaults())                                // POST /logout → /login?logout
        .csrf(csrf -> csrf
            .ignoringRequestMatchers("/h2-console/**"))                   // H2 콘솔은 CSRF 검사에서 제외
        .headers(headers -> headers
            .frameOptions(frame -> frame.sameOrigin()));                  // 같은 사이트의 <frame> 허용 (H2 콘솔)
    return http.build();
  }
```

**6) 세션 ID가 바뀌는 것 확인하기**

1. 로그아웃한 상태에서 로그인 화면을 연다.
2. 개발자 도구(`F12`) → `Application` 탭 → `Cookies` → `http://localhost:8080`에서 `JSESSIONID`의 값을 확인한다.
3. 로그인한 후 `JSESSIONID`의 값을 다시 확인한다. **값이 바뀌었다.** (세션 고정 공격 방어)
4. 로그아웃한 후에도 확인한다. 세션이 없어졌으므로 다음 요청에서 새 `JSESSIONID`가 만들어진다.

### 실습-6: 로그인한 사용자를 작성자로 사용하기

**1) 폼 객체에서 작성자 항목 지우기**

`board/BoardForm.java`에서 `writer` 필드(검증 애노테이션 포함)와 `getWriter()`, `setWriter()` 메서드를 **삭제**한다.
`from()` 메서드에서도 작성자를 설정하는 줄을 삭제한다.

```java
  // 게시글의 값으로 폼 객체를 만든다. (수정 폼에서 사용)
  public static BoardForm from(BoardResponse board) {
    BoardForm form = new BoardForm();
    form.setTitle(board.title());
    form.setContent(board.content());
    // form.setWriter(board.writer());    ← 삭제
    return form;
  }
```

**2) 폼 템플릿에서 작성자 입력 항목 지우기**

`templates/boards/form.html`에서 작성자 입력 항목(`<div class="field">` 하나)을 **삭제**한다. 바꾼 `form.html`은 다음과 같다.


**3) 화면 컨트롤러에서 로그인한 사용자를 작성자로 사용하기**

`board/BoardWebController.java`의 `create()` 메서드를 다음과 같이 바꾼다.

```java
import org.springframework.security.core.annotation.AuthenticationPrincipal;
import org.springframework.security.core.userdetails.UserDetails;

  // 등록 처리: POST /web/boards
  @PostMapping
  public String create(@Valid @ModelAttribute("boardForm") BoardForm form,
                       BindingResult bindingResult,
                       @AuthenticationPrincipal UserDetails loginUser,          // 추가: 로그인한 사용자
                       RedirectAttributes redirectAttributes) {
    if (bindingResult.hasErrors()) {
      return "boards/form";
    }
    BoardResponse created = boardService.create(
        new BoardCreateRequest(form.getTitle(), form.getContent(), loginUser.getUsername()));   // 작성자 = 로그인한 사용자
    redirectAttributes.addFlashAttribute("message", "게시글을 등록했습니다.");
    return "redirect:/web/boards/" + created.id();
  }
```

> `BindingResult`는 반드시 검증할 객체(`@Valid @ModelAttribute`) **바로 다음**에 두어야 한다. 그래서 `@AuthenticationPrincipal` 파라미터는 `BindingResult` 뒤에 둔다.

**4) REST API에서 인증한 사용자를 작성자로 사용하기**

`board/BoardController.java`의 `create()` 메서드를 다음과 같이 바꾼다. (8장에서 추가한 문서용 애노테이션은 그대로 둔다.)

```java
import org.springframework.security.core.annotation.AuthenticationPrincipal;
import org.springframework.security.core.userdetails.UserDetails;

  // 등록: POST /boards
  @PostMapping
  public ResponseEntity<BoardResponse> create(@RequestBody BoardCreateRequest request,
                                              @AuthenticationPrincipal UserDetails loginUser) {   // 추가
    if (request.title() == null || request.title().isBlank()) {
      return ResponseEntity.badRequest().build();
    }
    BoardResponse created = boardService.create(
        new BoardCreateRequest(request.title(), request.content(), loginUser.getUsername()));   // 작성자 = 인증한 사용자
    return ResponseEntity
        .created(URI.create("/boards/" + created.id()))
        .body(created);
  }
```

요청 본문의 `writer`는 무시하고, HTTP Basic 인증으로 확인한 사용자의 아이디를 작성자로 저장한다.

**5) 실행하고 확인하기**

애플리케이션을 다시 실행한다.

1. `hong`으로 로그인하고 `글쓰기`를 누른다. 등록 폼에 **작성자 입력 항목이 없다.**
2. 제목과 내용을 입력하고 등록한다. 상세 화면의 작성자가 `hong`이다.
3. 로그아웃하고 `kim`으로 로그인하여 글을 등록한다. 작성자가 `kim`이다.
4. `kim`으로 로그인한 상태에서 `hong`의 게시글을 열고 `수정`, `삭제`를 눌러 본다. **다른 사람의 글도 수정·삭제할 수 있다.** 이 문제는 14장에서 해결한다.

`http/security.http`의 등록 요청(3번)을 보낸다. 요청 본문의 `writer`는 `"홍길동"`이지만, 응답의 `writer`는 인증한 사용자 `user`이다.

```json
{
  "id": 25,
  "title": "보안 적용",
  "content": "HTTP Basic 인증으로 등록한다.",
  "writer": "user"
}
```

**6) 정리**

| 실습 | 확인한 내용 |
| --- | --- |
| 실습-1 | 사용자 테이블을 DDL로 정의하고 `UserEntity`, `UserRepository`를 만든다. |
| 실습-2 | `PasswordEncoder` 빈을 등록한다. 같은 비밀번호도 해시할 때마다 결과가 다르고(솔트), 비교는 `matches()`로 한다. |
| 실습-3 | `UserDetailsService`를 구현하면 데이터베이스의 사용자로 로그인한다. 저장된 값 앞의 `{bcrypt}`, `{noop}`으로 비교 방법이 정해진다. |
| 실습-4 | 회원가입: 입력 값 검증(`@Pattern`, `rejectValue`), 아이디 중복 확인, 비밀번호 해시 후 저장, 로그인 화면으로 리다이렉트 |
| 실습-5 | `loginPage("/login")`으로 로그인 화면을 직접 만든다. 실패 메시지는 아이디와 비밀번호를 구별하지 않는다. 로그아웃은 `POST` 폼. 로그인하면 세션 ID가 바뀐다. |
| 실습-6 | `@AuthenticationPrincipal UserDetails`로 로그인한 사용자를 받아 게시글 작성자로 사용한다. |
