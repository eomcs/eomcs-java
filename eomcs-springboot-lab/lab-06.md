# 6장. JPA 기초

5장까지 만든 게시판은 게시글을 메모리(`Map`)에 저장했기 때문에, 애플리케이션을 다시 실행하면 데이터가 모두 사라졌다.
데이터를 영구히 보관하려면 **데이터베이스**에 저장해야 한다.
이번 장에서는 자바 객체를 데이터베이스 테이블에 저장하는 기술인 **ORM**과 그 표준인 **JPA**를 이해하고, **Spring Data JPA**를 사용하여 SQL을 직접 작성하지 않고 데이터를 저장하고 조회하는 방법을 배운다.
데이터베이스는 별도로 설치할 필요가 없는 **H2 데이터베이스**를 파일 모드로 사용하며, 테이블은 **DDL 스크립트 파일**로 직접 정의한다.

## 데이터를 영구히 저장하려면

### 관계형 데이터베이스

**관계형 데이터베이스**(RDBMS)는 데이터를 **테이블**(표) 형태로 저장한다. 테이블은 **열**(Column)과 **행**(Row)으로 구성된다.
5장의 게시글(`Board`)을 테이블에 저장한다면 다음과 같은 모습이 된다.

`board` 테이블

| id | title | content | writer |
| --- | --- | --- | --- |
| 1 | 첫 번째 게시글 | 첫 번째 게시글의 내용입니다. | 홍길동 |
| 2 | 두 번째 게시글 | 두 번째 게시글의 내용입니다. | 임꺽정 |

데이터베이스를 다룰 때는 **SQL**(Structured Query Language)을 사용한다. SQL은 용도에 따라 다음과 같이 나뉜다.

| 분류 | 용도 | 예 |
| --- | --- | --- |
| **DDL**(Data Definition Language) | 테이블 같은 **구조를 정의**한다. | `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE` |
| **DML**(Data Manipulation Language) | **데이터를 다룬다.** | `INSERT`, `SELECT`, `UPDATE`, `DELETE` |

```sql
-- DDL: 테이블 만들기
CREATE TABLE board (
  id      BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title   VARCHAR(100)  NOT NULL,
  content VARCHAR(2000) NOT NULL,
  writer  VARCHAR(50)   NOT NULL
);

-- DML: 데이터 넣고 조회하기
INSERT INTO board (title, content, writer) VALUES ('첫 번째 게시글', '첫 번째 게시글의 내용입니다.', '홍길동');
SELECT id, title, content, writer FROM board;
```

### JDBC로 직접 저장할 때의 문제

자바에서 데이터베이스를 사용하는 기본 기술은 **JDBC**(Java Database Connectivity)이다.
JDBC로 게시글을 저장하고 조회하려면 다음과 같은 코드를 작성해야 한다.

```java
// 저장: 객체의 값을 하나씩 꺼내 SQL에 채운다.
String sql = "INSERT INTO board (title, content, writer) VALUES (?, ?, ?)";
try (PreparedStatement stmt = connection.prepareStatement(sql)) {
  stmt.setString(1, board.title());
  stmt.setString(2, board.content());
  stmt.setString(3, board.writer());
  stmt.executeUpdate();
}

// 조회: 결과의 값을 하나씩 꺼내 객체에 채운다.
String sql = "SELECT id, title, content, writer FROM board";
try (PreparedStatement stmt = connection.prepareStatement(sql);
     ResultSet rs = stmt.executeQuery()) {
  while (rs.next()) {
    boards.add(new Board(
        rs.getLong("id"),
        rs.getString("title"),
        rs.getString("content"),
        rs.getString("writer")));
  }
}
```

이 방식에는 다음과 같은 문제가 있다.

- **반복 코드가 많다.** 테이블마다 등록·조회·변경·삭제 SQL을 작성하고, 객체의 값과 SQL의 값을 하나씩 옮겨 담는 코드를 반복해야 한다.
- **변경에 약하다.** 게시글에 항목 하나를 추가하면, 그 항목을 사용하는 모든 SQL과 값을 옮기는 코드를 찾아 고쳐야 한다.
- **객체와 테이블의 구조가 다르다.** 객체는 다른 객체를 **참조**하지만, 테이블은 다른 테이블의 **키 값**을 저장한다. 이 차이를 개발자가 직접 맞춰야 한다. (7장의 연관관계에서 다룬다.)

## ORM과 JPA

### ORM

**ORM**(Object-Relational Mapping, 객체-관계 매핑)은 **객체와 테이블을 연결(매핑)해 두고, 객체를 저장하면 알맞은 SQL을 대신 만들어 실행해 주는 기술**이다.

| 객체 | ↔ | 테이블 |
| --- | --- | --- |
| 클래스 `BoardEntity` | ↔ | 테이블 `board` |
| 필드 `title` | ↔ | 열 `title` |
| 객체 하나 | ↔ | 행 하나 |

ORM을 사용하면 개발자는 SQL 대신 **객체를 다루는 코드**를 작성한다.

```java
boardJpaRepository.save(board);                         // → INSERT SQL이 만들어져 실행된다.
List<BoardEntity> boards = boardJpaRepository.findAll(); // → SELECT SQL이 만들어져 실행되고, 결과가 객체로 바뀐다.
```

### JPA와 Hibernate

**JPA**(Jakarta Persistence API)는 자바의 **ORM 표준 명세**이다.
JPA는 ORM을 어떻게 사용해야 하는지 정한 **인터페이스와 애노테이션의 모음**이며, 실제로 동작하는 코드는 들어 있지 않다.
JPA 명세를 실제로 구현한 라이브러리가 필요한데, 가장 널리 사용되는 구현체가 **Hibernate**(하이버네이트)이다.

| 구분 | 역할 | 비유 |
| --- | --- | --- |
| JPA | ORM의 표준 규칙 (인터페이스, 애노테이션) | 자동차 운전 방법의 표준 (핸들, 페달의 위치와 사용법) |
| Hibernate | JPA 규칙을 실제로 구현한 라이브러리 | 표준에 맞춰 만든 실제 자동차 |

개발자는 JPA의 애노테이션과 인터페이스로 코드를 작성하고, 실제 동작은 Hibernate가 처리한다.

> JPA의 애노테이션은 `jakarta.persistence` 패키지에 있다. 예전 자료에서 `javax.persistence`로 된 코드를 보면, Spring Boot 3 이후에는 `jakarta.persistence`로 바꿔야 한다. (2장 버전 관계 참고)

### Spring Data JPA

JPA를 직접 사용하더라도 저장, 조회, 삭제 같은 기본 코드는 엔티티마다 비슷하게 반복된다.
**Spring Data JPA**는 이런 반복 코드까지 없애 준다. 개발자는 **인터페이스만 선언**하면 되고, 구현 클래스는 스프링이 실행 중에 자동으로 만든다.

```java
public interface BoardJpaRepository extends JpaRepository<BoardEntity, Long> {
}
```

이 한 줄짜리 인터페이스만으로 다음 메서드를 사용할 수 있다.

| 메서드 | 기능 | 실행되는 SQL (예) |
| --- | --- | --- |
| `save(entity)` | 저장 (새 엔티티면 등록, 기존 엔티티면 변경) | `INSERT` 또는 `UPDATE` |
| `findById(id)` | 번호로 한 개 조회 (`Optional` 리턴) | `SELECT ... WHERE id = ?` |
| `findAll()` | 전체 조회 | `SELECT ...` |
| `count()` | 개수 조회 | `SELECT COUNT(*) ...` |
| `existsById(id)` | 있는지 확인 | `SELECT COUNT(*) ... WHERE id = ?` |
| `deleteById(id)` | 번호로 삭제 | `DELETE ... WHERE id = ?` |

`JpaRepository<BoardEntity, Long>`의 타입 파라미터는 다음과 같다.

| 타입 파라미터 | 의미 |
| --- | --- |
| `BoardEntity` | 이 리포지토리가 다루는 **엔티티** 클래스 |
| `Long` | 엔티티의 **식별자**(`@Id` 필드)의 타입 |

> 5장에서 `BoardRepository` 인터페이스와 `MemoryBoardRepository` 구현 클래스를 직접 만든 것과 비교해 보자.
> Spring Data JPA를 사용하면 **구현 클래스를 만들 필요가 없다.** 3장에서 배운 것처럼 스프링이 만든 구현 객체가 빈으로 등록되므로, 생성자로 주입받아 사용하면 된다.

> 메서드 이름만으로 조회 조건을 만드는 기능(Query Method)은 7장에서 다룬다.

### 전체 구조

지금까지 살펴본 기술은 다음과 같이 층을 이루어 동작한다.

```
[ 애플리케이션 코드 ]
    boardJpaRepository.save(board)
        │
        ▼
[ Spring Data JPA ]
    리포지토리 인터페이스의 구현 객체를 자동으로 만든다.
        │
        ▼
[ JPA (표준 명세) ]
    jakarta.persistence 애노테이션과 인터페이스
        │
        ▼
[ Hibernate (구현체) ]
    엔티티를 보고 SQL을 만들어 실행한다.
        │
        ▼
[ JDBC ]
    데이터베이스에 연결하여 SQL을 전달한다.
        │
        ▼
[ 데이터베이스 (H2) ]
```

이 라이브러리들은 스프링 부트의 **`spring-boot-starter-data-jpa`** 스타터 하나로 모두 추가된다.

## H2 데이터베이스

### H2란?

**H2**는 자바로 만든 가볍고 빠른 관계형 데이터베이스이다.
별도의 설치 없이 **라이브러리 하나를 추가하는 것만으로** 애플리케이션 안에서 함께 실행된다.
학습과 테스트에 많이 사용되며, 웹 브라우저로 데이터를 확인할 수 있는 **H2 콘솔**을 제공한다.

H2는 데이터를 저장하는 위치에 따라 여러 모드로 사용할 수 있다.

| 모드 | JDBC URL 예 | 데이터 저장 위치 | 애플리케이션을 다시 실행하면 |
| --- | --- | --- | --- |
| 메모리 모드 | `jdbc:h2:mem:hellodb` | 메모리 | 데이터가 **사라진다.** |
| **파일 모드** | `jdbc:h2:file:./data/hellodb` | 파일 | 데이터가 **남아 있다.** |
| 서버 모드 | `jdbc:h2:tcp://localhost/~/hellodb` | 별도 실행한 H2 서버 | 데이터가 남아 있다. |

이 교재에서는 데이터가 영구히 저장되는 것을 확인할 수 있도록 **파일 모드**를 사용한다.
`jdbc:h2:file:./data/hellodb`로 지정하면 프로젝트 폴더 아래의 `data` 폴더에 `hellodb.mv.db` 파일이 만들어지고, 이 파일에 데이터가 저장된다.

> 실무에서는 MySQL, PostgreSQL, Oracle 같은 데이터베이스를 사용한다.
> JPA를 사용하면 SQL을 Hibernate가 데이터베이스에 맞게 만들어 주므로, 데이터베이스를 바꿔도 Java 코드는 거의 바꿀 필요가 없다. 대부분 설정(JDBC URL)과 DDL 스크립트만 바꾸면 된다.

### 필요한 의존성

```groovy
dependencies {
  implementation 'org.springframework.boot:spring-boot-starter-data-jpa'   // JPA, Hibernate, Spring Data JPA, JDBC
  implementation 'org.springframework.boot:spring-boot-h2console'          // H2 콘솔 자동 구성
  runtimeOnly 'com.h2database:h2'                                          // H2 데이터베이스와 JDBC 드라이버
  testImplementation 'org.springframework.boot:spring-boot-starter-data-jpa-test'
}
```

> **Spring Boot 4 주의사항**: Spring Boot 3까지는 `spring.h2.console.enabled=true` 설정만으로 H2 콘솔을 사용할 수 있었다.
> Spring Boot 4부터는 자동 구성이 기능별 모듈로 나뉘어서, **`spring-boot-h2console` 모듈을 추가해야** H2 콘솔이 동작한다.
> H2 콘솔이 열리지 않는다면 이 의존성을 확인한다.

## 테이블 정의하기: DDL 스크립트

### 테이블은 누가 만드는가?

Hibernate는 엔티티 클래스를 보고 테이블을 만드는 SQL(DDL)을 **자동으로 만들어 실행**하는 기능이 있다.
설정 한 줄(`spring.jpa.hibernate.ddl-auto=update`)이면 테이블이 알아서 만들어지므로 편리해 보이지만, 이 교재에서는 **이 기능을 사용하지 않는다.**

| 방식 | 테이블을 만드는 주체 | 문제점 / 장점 |
| --- | --- | --- |
| 엔티티로 자동 생성 (`ddl-auto=create`, `update`) | Hibernate | 엔티티를 고치면 테이블 구조가 **개발자가 모르는 사이에** 바뀐다. 실수로 데이터가 사라질 수 있다. 열 순서, 제약 조건, 인덱스 등을 세밀하게 정할 수 없다. |
| **DDL 스크립트로 직접 정의** | 개발자 (SQL 파일) | 테이블 구조를 **SQL로 명확하게 정의**하고, 코드처럼 검토하고 이력을 관리할 수 있다. 실무 방식과 같다. |

실무에서 데이터베이스의 테이블은 애플리케이션보다 오래 살아남고, 여러 애플리케이션이 함께 사용하기도 한다.
그래서 테이블 구조는 엔티티에 맞춰 자동으로 바꾸지 않고, **DDL 스크립트로 먼저 정의한 후 엔티티를 테이블에 맞춰 작성**한다.

```
[ DDL 스크립트 (schema.sql) ]    개발자가 SQL로 작성한다.
        │ 정의
        ▼
[ 테이블 (board) ]
        ▲ 매핑
        │
[ 엔티티 (BoardEntity) ]         테이블에 맞춰 작성한다.
```

### 5장의 Board를 테이블로 정의하기

5장에서 사용한 `Board` record를 참고하여 테이블을 설계한다.

```java
public record Board(Long id, String title, String content, String writer) {
}
```

| `Board`의 구성 요소 | 열 이름 | 데이터 타입 | 제약 조건 | 설명 |
| --- | --- | --- | --- | --- |
| `Long id` | `id` | `BIGINT` | 기본 키, 자동 증가 | 게시글 번호. 데이터베이스가 자동으로 발급한다. |
| `String title` | `title` | `VARCHAR(100)` | `NOT NULL` | 제목 (최대 100자) |
| `String content` | `content` | `VARCHAR(2000)` | `NOT NULL` | 내용 (최대 2000자) |
| `String writer` | `writer` | `VARCHAR(50)` | `NOT NULL` | 작성자 (최대 50자) |

이 설계를 DDL로 작성하면 다음과 같다.

```sql
CREATE TABLE IF NOT EXISTS board (
  id      BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title   VARCHAR(100)  NOT NULL,
  content VARCHAR(2000) NOT NULL,
  writer  VARCHAR(50)   NOT NULL
);
```

| 구문 | 의미 |
| --- | --- |
| `CREATE TABLE IF NOT EXISTS` | 테이블이 **없을 때만** 만든다. 이미 있으면 아무것도 하지 않으므로, 여러 번 실행해도 기존 데이터가 지워지지 않는다. |
| `BIGINT` | Java의 `long`/`Long`에 해당하는 정수 타입 |
| `GENERATED BY DEFAULT AS IDENTITY` | 값을 지정하지 않으면 데이터베이스가 1, 2, 3, ... 순서로 번호를 **자동 발급**한다. |
| `PRIMARY KEY` | 기본 키. 각 행을 구별하는 값으로, 중복되거나 비어 있을 수 없다. |
| `VARCHAR(n)` | 최대 `n`자까지 저장하는 문자열 타입 |
| `NOT NULL` | 값이 반드시 있어야 한다. |

### 애플리케이션이 시작될 때 DDL 스크립트 실행하기

스프링 부트는 애플리케이션이 시작될 때 **SQL 스크립트 파일을 실행하는 기능**을 제공한다.
DDL 스크립트를 `src/main/resources/db/schema.sql` 파일로 저장하고, 다음과 같이 설정한다.

```properties
# 애플리케이션이 시작될 때 SQL 스크립트 실행
spring.sql.init.mode=always
spring.sql.init.schema-locations=classpath:db/schema.sql
```

| 설정 | 의미 |
| --- | --- |
| `spring.sql.init.mode` | SQL 스크립트를 실행할지 정한다. `always`는 항상, `never`는 실행하지 않음, `embedded`(기본값)는 메모리 데이터베이스일 때만 실행한다. |
| `spring.sql.init.schema-locations` | 실행할 DDL 스크립트 파일의 위치. `classpath:`는 `src/main/resources` 폴더를 뜻한다. |

> 기본값(`embedded`)은 **메모리 모드**의 데이터베이스에서만 스크립트를 실행한다. 파일 모드를 사용하므로 `always`로 지정한다.

> SQL 스크립트는 JPA(Hibernate)가 준비되기 **전에** 실행된다. 그래서 Hibernate가 시작될 때는 테이블이 이미 만들어져 있다.

> 이 기능은 개발과 학습에 편리한 방법이다. 운영 환경에서는 데이터베이스 관리자가 DDL을 직접 실행하거나, Flyway·Liquibase 같은 **데이터베이스 변경 관리 도구**로 DDL의 변경 이력을 관리하며 적용한다.

### Hibernate는 검사만 하게 하기: ddl-auto=validate

`spring.jpa.hibernate.ddl-auto`는 Hibernate가 테이블을 어떻게 다룰지 정하는 설정이다.

| 값 | 애플리케이션이 시작될 때 | 테이블을 바꾸는가? |
| --- | --- | --- |
| `none` | 아무것도 하지 않는다. | 바꾸지 않는다. |
| **`validate`** | 엔티티와 테이블이 맞는지 **검사만** 한다. 맞지 않으면 실행에 실패한다. | 바꾸지 않는다. |
| `update` | 테이블이 없으면 만들고, 엔티티에 새 필드가 생기면 열을 추가한다. | **바꾼다.** |
| `create` | 테이블을 지우고 새로 만든다. 기존 데이터가 사라진다. | **바꾼다.** |
| `create-drop` | 테이블을 지우고 새로 만들고, 종료할 때 다시 지운다. | **바꾼다.** |

이 교재에서는 테이블을 DDL 스크립트로만 관리하므로 `validate`를 사용한다.
Hibernate는 테이블을 만들거나 바꾸지 않고, 엔티티가 테이블과 맞게 작성되었는지만 확인한다.
엔티티에 있는 필드에 해당하는 열이 테이블에 없으면 애플리케이션이 시작되지 않으므로, **실수를 일찍 발견**할 수 있다.

> `ddl-auto`를 설정하지 않으면 스프링 부트는 데이터베이스 종류와 URL에 따라 `create-drop`을 기본값으로 사용할 수도 있다. 그러면 DDL 스크립트로 만든 테이블이 지워지고 다시 만들어질 수 있으므로, 반드시 **명시적으로** 설정한다.

### 데이터베이스와 JPA 설정 정리

`application.properties`에 추가할 설정을 모두 모으면 다음과 같다.

```properties
# 데이터베이스 연결 (H2 파일 모드)
spring.datasource.url=jdbc:h2:file:./data/hellodb
spring.datasource.username=sa
spring.datasource.password=

# H2 콘솔
spring.h2.console.enabled=true
spring.h2.console.path=/h2-console

# 애플리케이션이 시작될 때 DDL 스크립트 실행
spring.sql.init.mode=always
spring.sql.init.schema-locations=classpath:db/schema.sql

# Hibernate는 엔티티와 테이블이 맞는지 검사만 한다.
spring.jpa.hibernate.ddl-auto=validate

# 실행되는 SQL을 로그에 출력
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

| 설정 | 의미 |
| --- | --- |
| `spring.datasource.url` | 연결할 데이터베이스의 주소(JDBC URL) |
| `spring.datasource.username` / `password` | 데이터베이스 사용자 이름과 비밀번호. H2의 기본 사용자는 `sa`, 비밀번호는 없다. |
| `spring.h2.console.enabled` / `path` | H2 콘솔을 사용하고, 콘솔의 주소를 지정한다. |
| `spring.jpa.show-sql` | Hibernate가 실행하는 SQL을 콘솔에 출력한다. |
| `spring.jpa.properties.hibernate.format_sql` | 출력하는 SQL을 보기 좋게 줄바꿈한다. |

> JDBC 드라이버 클래스(`org.h2.Driver`)는 JDBC URL을 보고 스프링 부트가 자동으로 찾으므로 설정하지 않아도 된다.
> 데이터베이스 연결 객체(`DataSource`)도 2장에서 배운 **자동 구성**이 만들어 준다.

## 엔티티

### 엔티티란?

**엔티티**(Entity)는 데이터베이스 테이블과 매핑되는 클래스이다. 엔티티 객체 하나가 테이블의 행 하나에 해당한다.
클래스에 `@Entity`를 붙이면 JPA가 관리하는 엔티티가 된다.

앞에서 DDL로 정의한 `board` 테이블에 맞춰 엔티티를 작성하면 다음과 같다.

```java
package com.example.hello.board;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity                                                   // ① 엔티티 클래스
@Table(name = "board")                                    // ② 매핑할 테이블 이름
public class BoardEntity {

  @Id                                                     // ③ 식별자 (기본 키)
  @GeneratedValue(strategy = GenerationType.IDENTITY)     // ④ 번호를 데이터베이스가 자동 발급
  private Long id;

  private String title;                                   // ⑤ title 열과 매핑
  private String content;
  private String writer;

  protected BoardEntity() {                               // ⑥ JPA가 사용하는 기본 생성자
  }

  public BoardEntity(String title, String content, String writer) {
    this.title = title;
    this.content = content;
    this.writer = writer;
  }

  // getter 메서드 ...
}
```

### 엔티티 매핑 애노테이션

**① `@Entity`**

이 클래스가 엔티티임을 표시한다.

**② `@Table`**

엔티티와 매핑할 테이블의 이름을 지정한다. `@Table`을 생략하면 **클래스 이름**을 테이블 이름으로 사용한다. (`BoardEntity` → `board_entity` 테이블)
DDL로 만든 테이블의 이름은 `board`이므로 `@Table(name = "board")`로 지정한다.

**③ `@Id`**

테이블의 **기본 키**(Primary Key)와 매핑되는 필드를 지정한다. 모든 엔티티에는 `@Id`가 반드시 하나 있어야 한다.

**④ `@GeneratedValue`**

기본 키 값을 누가, 어떻게 만드는지 지정한다. 5장에서 `AtomicLong`으로 번호를 직접 발급하던 일을 데이터베이스에 맡기는 것이다.

| 전략 | 방식 | 주로 사용하는 데이터베이스 |
| --- | --- | --- |
| `IDENTITY` | 데이터를 넣을 때 데이터베이스가 번호를 자동 증가시킨다. | MySQL, H2, PostgreSQL |
| `SEQUENCE` | 데이터베이스의 시퀀스 객체에서 번호를 가져온다. | Oracle, PostgreSQL, H2 |
| `AUTO` (기본값) | 데이터베이스에 맞는 전략을 Hibernate가 선택한다. | - |

DDL에서 `id` 열을 `GENERATED BY DEFAULT AS IDENTITY`(자동 증가)로 정의했으므로, 엔티티에서는 **`IDENTITY`** 전략을 사용한다.
**DDL과 엔티티의 설정이 서로 맞아야 한다.**

**⑤ 필드와 열의 매핑**

`@Column` 없이도 모든 필드는 **같은 이름의 열**과 매핑된다. (`title` 필드 → `title` 열)
필드 이름과 열 이름이 다르면 `@Column(name = "열이름")`으로 지정한다.

```java
@Column(name = "writer_name")      // writer 필드를 writer_name 열과 매핑
private String writer;
```

> 스프링 부트는 Java의 **카멜 표기법**(camelCase) 이름을 데이터베이스의 **스네이크 표기법**(snake_case) 이름으로 바꿔서 매핑한다.
> 예를 들어 `createdAt` 필드는 `created_at` 열과 매핑된다.

> `@Column`에는 `nullable`, `length` 같은 속성도 있다. 이 속성은 Hibernate가 테이블을 **자동으로 만들 때** 사용하는 정보이다.
> 이 교재처럼 DDL로 테이블을 정의하면 `NOT NULL`, 길이 같은 제약 조건은 **DDL이 결정**한다.

**⑥ 기본 생성자**

JPA는 데이터베이스에서 조회한 데이터로 엔티티 객체를 만들 때 **파라미터가 없는 기본 생성자**를 사용한다. 그래서 엔티티에는 반드시 기본 생성자가 있어야 한다.
다른 개발자가 실수로 빈 객체를 만들지 못하도록 접근 범위를 `protected`로 지정하는 것이 일반적이다.

### 엔티티 클래스의 규칙

| 규칙 | 이유 |
| --- | --- |
| `@Entity`와 `@Id`가 있어야 한다. | 엔티티임을 표시하고 행을 구별하기 위해 |
| 기본 생성자(`public` 또는 `protected`)가 있어야 한다. | JPA가 객체를 만들기 위해 |
| 클래스를 `final`로 선언하지 않는다. | Hibernate가 엔티티를 상속한 대리 객체(프록시)를 만들기 위해 (7장 지연 로딩) |
| **`record`는 엔티티로 사용할 수 없다.** | `record`는 `final`이고 필드 값을 바꿀 수 없어서 위 규칙을 지킬 수 없다. |

> 5장의 `Board`는 `record`이므로 엔티티로 사용할 수 없다. 그래서 같은 게시글 데이터를 다루는 **엔티티 클래스 `BoardEntity`를 따로** 만들었다.
> 지금은 `board` 패키지에 `Board`(record)와 `BoardEntity`(엔티티)가 함께 있다. 두 클래스의 역할을 나누고 게시판 API가 `BoardEntity`를 사용하도록 바꾸는 방법은 8장에서 다룬다.

> 엔티티에는 `setter` 메서드를 무분별하게 만들지 않는다. 값을 바꿔야 할 때는 "제목과 내용을 수정한다"처럼 의미가 드러나는 메서드를 만든다. (7장에서 다룬다.)

## 리포지토리

### Spring Data JPA 리포지토리 만들기

엔티티를 저장하고 조회하는 **리포지토리**(Repository)는 `JpaRepository`를 상속한 **인터페이스**로 만든다.

```java
package com.example.hello.board;

import org.springframework.data.jpa.repository.JpaRepository;

public interface BoardJpaRepository extends JpaRepository<BoardEntity, Long> {
}
```

- 구현 클래스를 만들지 않는다. Spring Data JPA가 실행 중에 구현 객체를 만들어 **빈으로 등록**한다.
- `@Repository`를 붙이지 않아도 된다. `JpaRepository`를 상속한 인터페이스는 스프링 부트가 자동으로 찾아서 등록한다.

> 5장에서 만든 `BoardRepository`(직접 만든 인터페이스)와 이름이 겹치지 않도록, JPA 리포지토리의 이름은 `BoardJpaRepository`로 한다.
> 5장의 `MemoryBoardRepository`가 "메모리에 저장하는 게시글 리포지토리"라면, `BoardJpaRepository`는 "JPA로 저장하는 게시글 리포지토리"이다.

사용하는 쪽에서는 3장에서 배운 대로 **생성자로 주입받는다.**

```java
@Component
public class BoardDataRunner implements CommandLineRunner {

  private final BoardJpaRepository boardJpaRepository;

  public BoardDataRunner(BoardJpaRepository boardJpaRepository) {   // 스프링이 만든 구현 객체가 주입된다.
    this.boardJpaRepository = boardJpaRepository;
  }
  ...
}
```

### 저장과 조회

```java
// 저장: id가 없는 새 엔티티이므로 INSERT가 실행되고, 데이터베이스가 발급한 번호가 id에 채워진다.
BoardEntity saved = boardJpaRepository.save(new BoardEntity("제목", "내용", "홍길동"));
System.out.println(saved.getId());          // 1

// 전체 조회
List<BoardEntity> boards = boardJpaRepository.findAll();

// 번호로 조회: 없을 수도 있으므로 Optional을 리턴한다. (5장과 같은 방식)
Optional<BoardEntity> board = boardJpaRepository.findById(1L);

// 개수 조회
long count = boardJpaRepository.count();
```

> 등록 전에는 `id`가 `null`이었다가, `save()` 후에는 데이터베이스가 발급한 번호가 채워진다.
> `@GeneratedValue(strategy = GenerationType.IDENTITY)`로 번호 발급을 데이터베이스에 맡겼기 때문이다.

> 조회한 엔티티의 값을 변경하고 삭제하는 방법은 7장의 CRUD에서 다룬다.

## 정리

| 용어 | 의미 |
| --- | --- |
| ORM | 객체와 테이블을 매핑해 두고, 객체를 다루면 SQL을 대신 만들어 실행해 주는 기술 |
| JPA | 자바 ORM의 표준 명세 (`jakarta.persistence`) |
| Hibernate | JPA 명세를 구현한 라이브러리. 실제로 SQL을 만들어 실행한다. |
| Spring Data JPA | 리포지토리 인터페이스만 선언하면 구현 객체를 자동으로 만들어 주는 스프링 프로젝트 |
| H2 | 설치 없이 애플리케이션 안에서 실행되는 자바 데이터베이스. 파일 모드로 데이터를 영구 저장한다. |
| DDL 스크립트 | 테이블 구조를 정의하는 SQL 파일(`schema.sql`). 테이블은 엔티티가 아니라 DDL로 정의한다. |
| `ddl-auto=validate` | Hibernate가 테이블을 바꾸지 않고, 엔티티와 테이블이 맞는지 검사만 하게 하는 설정 |
| 엔티티 | `@Entity`가 붙은, 테이블과 매핑되는 클래스. `record`로는 만들 수 없다. |
| `@Table` / `@Id` / `@GeneratedValue` | 매핑할 테이블 이름 / 기본 키 필드 / 기본 키 생성 방식 |
| `JpaRepository<엔티티, ID타입>` | 저장, 조회, 삭제 등 기본 메서드를 제공하는 리포지토리 인터페이스 |

## 실습

이번 장의 실습은 5장까지 사용한 `hello` 프로젝트의 `board` 패키지에서 이어서 진행한다.
5장에서 만든 게시판 API(메모리 저장)는 그대로 두고, 같은 패키지에 JPA로 게시글을 저장하는 엔티티와 리포지토리를 추가한다.

실습을 마치면 다음 파일이 추가된다.

```
hello
├── data
│   └── hellodb.mv.db                     ← H2 데이터베이스 파일 (자동 생성)
└── src/main
    ├── java/com/example/hello/board
    │   ├── Board.java                    ← (5장) 게시글 record
    │   ├── ...                           ← (5장) 그 밖의 게시판 API 파일
    │   ├── BoardEntity.java              ← 엔티티              (실습-3)
    │   ├── BoardJpaRepository.java       ← JPA 리포지토리       (실습-4)
    │   └── BoardDataRunner.java          ← 실행 확인용 코드       (실습-4)
    └── resources
        ├── application.properties
        └── db
            └── schema.sql                ← DDL 스크립트         (실습-2)
```

### 실습-1: H2 데이터베이스 연결하기

`build.gradle`의 `dependencies` 블록에 다음 네 줄을 추가한다.

```groovy
dependencies {

  implementation 'org.springframework.boot:spring-boot-starter-data-jpa'          // 추가

  testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}
```

> 2장에서 Actuator 스타터를 추가했다면 그 줄도 그대로 둔다.
> VS Code에서 `build.gradle`을 저장한 후 빌드 설정을 동기화할지 묻는 알림이 뜨면 `Yes`를 누른다.

**2) 데이터베이스 연결 설정하기**

`src/main/resources/application.properties`에 다음 설정을 추가한다. 이전 장에서 추가한 설정이 있으면 그대로 둔다.

```properties
# 데이터베이스 연결 (H2 파일 모드)

spring.datasource.username=sa
spring.datasource.password=

# H2 콘솔

```

> 아직 테이블과 엔티티가 없으므로 지금은 `ddl-auto`를 `none`으로 둔다. 실습-3에서 `validate`로 바꾼다.

**3) 데이터베이스 파일을 Git에서 제외하기**

데이터베이스 파일은 실행할 때마다 내용이 바뀌므로 Git으로 관리하지 않는다.
프로젝트 폴더의 `.gitignore` 파일 맨 아래에 다음 줄을 추가한다.

```
### H2 데이터베이스 파일 ###
data/
```

**4) 실행하기**

애플리케이션을 실행한다.

```bash
# macOS
./gradlew bootRun
```

```powershell
# Windows (PowerShell)
.\gradlew bootRun
```

실행 로그에서 다음과 비슷한 내용을 찾는다. (형식은 버전에 따라 조금 다를 수 있다.)

```
... HikariPool-1 - Starting...
... HikariPool-1 - Added connection conn0: url=jdbc:h2:file:./data/hellodb user=SA
... HikariPool-1 - Start completed.
... H2 console available at '/h2-console'. Database available at 'jdbc:h2:file:./data/hellodb'
```

- `HikariPool`: 스프링 부트가 자동으로 만든 **데이터베이스 연결 풀**(Connection Pool)이다. 데이터베이스 연결을 미리 만들어 두고 재사용하여 성능을 높인다.
- `H2 console available at '/h2-console'`: H2 콘솔을 사용할 수 있다는 뜻이다.

VS Code 탐색기에서 프로젝트 폴더에 `data` 폴더와 `hellodb.mv.db` 파일이 생긴 것을 확인한다.

**5) H2 콘솔 접속하기**

웹 브라우저에서 [http://localhost:8080/h2-console](http://localhost:8080/h2-console) 에 접속한다. 로그인 화면에서 다음과 같이 입력하고 `Connect` 버튼을 누른다.

| 항목 | 입력 값 |
| --- | --- |
| Driver Class | `org.h2.Driver` (그대로 둔다) |
| JDBC URL | `jdbc:h2:file:./data/hellodb` |
| User Name | `sa` |
| Password | (비워 둔다) |

> **JDBC URL은 `application.properties`에 설정한 값과 정확히 같아야 한다.**
> 기본으로 입력되어 있는 `jdbc:h2:~/test`로 접속하면 홈 폴더에 다른 데이터베이스 파일이 새로 만들어진다.

접속하면 왼쪽에 데이터베이스의 구조가 표시된다. 아직 테이블을 만들지 않았으므로 우리가 만든 테이블은 없다.

> 파일 모드의 H2 데이터베이스는 한 번에 하나의 프로그램만 사용할 수 있다.
> 애플리케이션이 실행 중일 때는 애플리케이션 안의 H2 콘솔로 접속하고, 다른 데이터베이스 도구로 같은 파일을 열지 않는다.

확인한 후에는 `Ctrl + C`를 눌러 애플리케이션을 종료한다.

### 실습-2: DDL 스크립트로 테이블 정의하기

5장의 `Board` record를 참고하여 게시글 테이블을 DDL로 정의하고, 애플리케이션이 시작될 때 실행되도록 설정한다.

**1) DDL 스크립트 파일 만들기**

`src/main/resources` 폴더 아래에 `db` 폴더를 만들고, 그 안에 `schema.sql` 파일을 만든다. 다음과 같이 작성한다.

```sql
-- 게시글 테이블
-- 5장의 Board(id, title, content, writer)를 참고하여 정의한다.
CREATE TABLE IF NOT EXISTS board (
  id      BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,  -- 게시글 번호 (자동 증가)
  title   VARCHAR(100)  NOT NULL,                                      -- 제목
  content VARCHAR(2000) NOT NULL,                                      -- 내용
  writer  VARCHAR(50)   NOT NULL                                       -- 작성자
);
```

> SQL에서 `--` 뒤의 내용은 주석이다.

**2) 스크립트 실행 설정하기**

`application.properties`에 다음 설정을 추가한다.

```properties
# 애플리케이션이 시작될 때 DDL 스크립트 실행
spring.sql.init.mode=always
spring.sql.init.schema-locations=classpath:db/schema.sql
```

**3) 실행하고 테이블 확인하기**

애플리케이션을 실행하고 [http://localhost:8080/h2-console](http://localhost:8080/h2-console) 에 접속한다. (JDBC URL: `jdbc:h2:file:./data/hellodb`)
왼쪽 목록에 `BOARD` 테이블이 생긴 것을 확인하고, 테이블 이름 앞의 `+`를 눌러 열 목록(`ID`, `TITLE`, `CONTENT`, `WRITER`)을 펼쳐 본다.

> H2 콘솔은 테이블과 열 이름을 대문자로 표시한다. SQL에서는 대문자와 소문자를 구별하지 않으므로 같은 이름이다.

H2 콘솔의 입력 창에 다음 SQL을 입력하고 `Run` 버튼을 누르면 테이블의 구조를 자세히 볼 수 있다.

```sql
SHOW COLUMNS FROM board;
```

**4) 한 번 더 실행하기**

애플리케이션을 종료하고 다시 실행한다. 오류 없이 실행되는 것을 확인한다.
`schema.sql`은 실행할 때마다 다시 실행되지만, `CREATE TABLE IF NOT EXISTS`는 테이블이 **이미 있으면 아무것도 하지 않기** 때문이다.

> `IF NOT EXISTS`를 빼고 `CREATE TABLE board (...)`로만 작성하면, 두 번째 실행부터는 "테이블이 이미 있다"는 오류가 발생하여 애플리케이션이 시작되지 않는다.

### 실습-3: 테이블에 맞춰 엔티티 만들기

`board` 테이블에 맞춰 엔티티 클래스를 작성하고, Hibernate가 엔티티와 테이블을 검사하도록 설정한다.

**1) 엔티티 클래스 만들기**

`board` 폴더에 `BoardEntity.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.board;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "board")
public class BoardEntity {

  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  private String title;

  private String content;

  private String writer;

  // JPA가 사용하는 기본 생성자
  protected BoardEntity() {
  }

  // 새 게시글을 만들 때 사용하는 생성자
  public BoardEntity(String title, String content, String writer) {
    this.title = title;
    this.content = content;
    this.writer = writer;
  }

  public Long getId() {
    return id;
  }

  public String getTitle() {
    return title;
  }

  public String getContent() {
    return content;
  }

  public String getWriter() {
    return writer;
  }

  @Override
  public String toString() {
    return "BoardEntity[id=" + id + ", title=" + title + ", writer=" + writer + "]";
  }
}
```

> `import` 문의 패키지가 `jakarta.persistence`인지 확인한다. VS Code의 자동 완성으로 `import`할 때 다른 패키지의 같은 이름 애노테이션을 선택하지 않도록 주의한다.

DDL과 엔티티를 비교해 보자.

| DDL (`schema.sql`) | 엔티티 (`BoardEntity`) |
| --- | --- |
| `CREATE TABLE board` | `@Entity`, `@Table(name = "board")` |
| `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `@Id @GeneratedValue(strategy = GenerationType.IDENTITY) Long id` |
| `title VARCHAR(100) NOT NULL` | `String title` |
| `content VARCHAR(2000) NOT NULL` | `String content` |
| `writer VARCHAR(50) NOT NULL` | `String writer` |

**2) JPA 설정 바꾸기**

`application.properties`에서 `ddl-auto`를 `validate`로 바꾸고, 실행되는 SQL을 로그에 출력하는 설정을 추가한다.

```properties
# Hibernate는 엔티티와 테이블이 맞는지 검사만 한다.
spring.jpa.hibernate.ddl-auto=validate

# 실행되는 SQL을 로그에 출력
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

**3) 실행하기**

애플리케이션을 실행한다. 오류 없이 실행되면 `BoardEntity`가 `board` 테이블과 **맞게** 작성된 것이다.
로그에 `create table` SQL이 출력되지 않는 것도 확인한다. Hibernate는 테이블을 만들지 않고 검사만 했다.

**4) (확인) 엔티티와 테이블이 맞지 않으면**

애플리케이션을 종료하고, `BoardEntity.java`에 테이블에 없는 필드를 잠시 추가해 본다.

```java
  private String writer;

  private int viewCount;          // 추가: 조회수 (테이블에는 view_count 열이 없다)
```

애플리케이션을 실행하면 다음과 비슷한 오류가 발생하며 실행에 실패한다. (형식은 버전에 따라 다를 수 있다.)

```
Schema-validation: missing column [view_count] in table [board]
```

엔티티의 `viewCount` 필드와 매핑될 `view_count` 열이 테이블에 없다는 뜻이다.

- `ddl-auto=update`였다면 Hibernate가 `view_count` 열을 테이블에 **몰래 추가**했을 것이다.
- `validate`는 테이블을 바꾸지 않고, 엔티티와 테이블이 **다르다는 것을 알려 준다.**

테이블에 열을 추가해야 한다면, 개발자가 DDL 스크립트를 고쳐서 테이블을 바꾼 다음 엔티티를 고쳐야 한다.
확인한 후에는 추가한 `viewCount` 필드를 삭제하고, 애플리케이션이 다시 정상적으로 실행되는지 확인한다.

> 이미 만들어진 테이블에 열을 추가하려면 `ALTER TABLE board ADD COLUMN view_count INT DEFAULT 0 NOT NULL;`처럼 **테이블을 변경하는 DDL**을 실행해야 한다.
> `CREATE TABLE IF NOT EXISTS` 문장만 고치면, 테이블이 이미 있으므로 실행되지 않는다. 운영 환경에서 이런 변경 이력을 관리하는 도구가 Flyway, Liquibase이다.

### 실습-4: JPA 리포지토리로 데이터 저장하고 조회하기

**1) 리포지토리 인터페이스 만들기**

`board` 폴더에 `BoardJpaRepository.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.board;

import org.springframework.data.jpa.repository.JpaRepository;

public interface BoardJpaRepository extends JpaRepository<BoardEntity, Long> {
}
```

인터페이스 선언 한 줄이 전부이다. 구현 클래스는 만들지 않는다.

**2) 실행 확인용 코드 만들기**

게시판 API가 `BoardJpaRepository`를 사용하도록 바꾸는 것은 8장에서 한다.
이번 장에서는 애플리케이션이 시작될 때 리포지토리를 사용하는 코드를 실행하여 결과를 확인한다.
`board` 폴더에 `BoardDataRunner.java` 파일을 만들고 다음과 같이 작성한다.

```java
package com.example.hello.board;

import org.springframework.boot.CommandLineRunner;
import org.springframework.stereotype.Component;

@Component
public class BoardDataRunner implements CommandLineRunner {

  private final BoardJpaRepository boardJpaRepository;

  public BoardDataRunner(BoardJpaRepository boardJpaRepository) {
    this.boardJpaRepository = boardJpaRepository;
  }

  @Override
  public void run(String... args) {
    System.out.println("========== BoardDataRunner 시작 ==========");

    // 게시글이 하나도 없을 때만 샘플 게시글을 저장한다.
    if (boardJpaRepository.count() == 0) {
      BoardEntity board1 = new BoardEntity("첫 번째 게시글", "JPA로 저장한 첫 번째 게시글입니다.", "홍길동");
      System.out.println("저장 전 id: " + board1.getId());

      BoardEntity saved = boardJpaRepository.save(board1);
      System.out.println("저장 후 id: " + saved.getId());

      boardJpaRepository.save(new BoardEntity("두 번째 게시글", "JPA로 저장한 두 번째 게시글입니다.", "임꺽정"));
    }

    // 전체 조회
    System.out.println("저장된 게시글 수: " + boardJpaRepository.count());
    for (BoardEntity board : boardJpaRepository.findAll()) {
      System.out.println(board);
    }

    // 번호로 조회
    boardJpaRepository.findById(1L)
        .ifPresent(board -> System.out.println("1번 게시글: " + board.getTitle()));

    System.out.println("========== BoardDataRunner 끝 ==========");
  }
}
```

> `CommandLineRunner`는 스프링 부트가 제공하는 인터페이스이다.
> 이 인터페이스를 구현한 빈이 있으면, 스프링 부트는 애플리케이션이 모두 시작된 후 그 빈의 `run()` 메서드를 호출한다.
> 여기서는 JPA의 동작을 확인하는 용도로 사용한다.

**3) 실행하고 확인하기**

애플리케이션을 실행하고 로그를 확인한다. 다음과 비슷한 내용이 출력된다. (SQL 형식은 버전에 따라 다를 수 있다.)

```
========== BoardDataRunner 시작 ==========
Hibernate: 
    select
        count(*) 
    from
        board be1_0
저장 전 id: null
Hibernate: 
    insert 
    into
        board
        (content, title, writer, id) 
    values
        (?, ?, ?, default)
저장 후 id: 1
Hibernate: 
    insert 
    into
        board
        ...
저장된 게시글 수: 2
Hibernate: 
    select
        be1_0.id,
        be1_0.content,
        be1_0.title,
        be1_0.writer 
    from
        board be1_0
BoardEntity[id=1, title=첫 번째 게시글, writer=홍길동]
BoardEntity[id=2, title=두 번째 게시글, writer=임꺽정]
...

```

다음을 확인한다.

- `count()`, `save()`, `findAll()`, `findById()`를 호출할 때마다 알맞은 **SQL이 자동으로 만들어져 실행**되었다.
- `save()` 전에는 `id`가 `null`이었지만, 저장 후에는 데이터베이스가 발급한 번호(`1`)가 채워졌다.
- `findAll()`의 결과는 테이블의 행이 **`BoardEntity` 객체로 변환**된 것이다.
- 우리가 작성한 Java 코드에는 SQL도, 리포지토리 구현 클래스도 없다.

**4) H2 콘솔에서 데이터 확인하기**

[http://localhost:8080/h2-console](http://localhost:8080/h2-console) 에 접속하여 다음 SQL을 실행한다.

```sql
SELECT * FROM board;
```

JPA로 저장한 게시글 두 개가 테이블의 행으로 저장된 것을 확인한다.

> 왼쪽 목록에서 `BOARD` 테이블 이름을 클릭하면 `SELECT * FROM BOARD` SQL이 자동으로 입력된다.

**5) 5장의 게시판 API와 비교하기**

`http/board.http`에서 `GET {{baseUrl}}/boards`를 요청해 본다.
응답되는 게시글은 H2 데이터베이스의 게시글이 **아니라**, 5장의 `MemoryBoardRepository`에 저장된 게시글이다.
게시판 API는 아직 `MemoryBoardRepository`를 사용하고 있기 때문이다. 게시판 API가 데이터베이스를 사용하도록 바꾸는 것은 8장에서 한다.

### 실습-5: 데이터가 영구히 저장되는지 확인하기

**1) 다시 실행하기**

애플리케이션을 종료하고 다시 실행한다. 로그를 확인한다.

```
========== BoardDataRunner 시작 ==========
...
저장된 게시글 수: 2
BoardEntity[id=1, title=첫 번째 게시글, writer=홍길동]
BoardEntity[id=2, title=두 번째 게시글, writer=임꺽정]
1번 게시글: 첫 번째 게시글
========== BoardDataRunner 끝 ==========
```

- `저장 전 id`, `저장 후 id`가 출력되지 않았다. 이미 게시글이 있어서(`count() == 0`이 거짓) 샘플을 저장하지 않았기 때문이다.
- 이전 실행에서 저장한 게시글 두 개가 **그대로 남아 있다.** 데이터가 `data/hellodb.mv.db` 파일에 저장되어 있기 때문이다.
- `schema.sql`도 다시 실행되었지만, `CREATE TABLE IF NOT EXISTS`이므로 테이블과 데이터가 그대로 유지되었다.

5장의 메모리 저장소에서는 다시 실행하면 등록한 게시글이 사라졌던 것과 비교해 보자.

**2) H2 콘솔에서 SQL로 게시글 추가하기**

JPA로 저장한 데이터와 SQL로 저장한 데이터가 **같은 테이블**에 저장된다는 것을 확인한다.
[http://localhost:8080/h2-console](http://localhost:8080/h2-console) 에 접속하여 다음 SQL을 실행한다.

```sql
INSERT INTO board (title, content, writer)
VALUES ('SQL로 쓴 게시글', 'H2 콘솔에서 SQL로 직접 저장했습니다.', '유관순');

SELECT * FROM board;
```

`id`를 지정하지 않았는데도 `3`이 자동으로 채워진 것을 확인한다. DDL에서 `id` 열을 **자동 증가**(`GENERATED BY DEFAULT AS IDENTITY`)로 정의했기 때문이다.

애플리케이션을 종료하고 다시 실행한다. `BoardDataRunner`의 출력을 확인한다.

```
저장된 게시글 수: 3
BoardEntity[id=1, title=첫 번째 게시글, writer=홍길동]
BoardEntity[id=2, title=두 번째 게시글, writer=임꺽정]
BoardEntity[id=3, title=SQL로 쓴 게시글, writer=유관순]
```

SQL로 직접 추가한 게시글도 `findAll()`로 조회되어 `BoardEntity` 객체로 변환되었다.
JPA는 데이터베이스의 테이블을 읽고 쓸 뿐이므로, 어떤 방법으로 저장했든 테이블에 있는 데이터는 모두 엔티티로 조회할 수 있다.

**3) (확인) DDL의 NOT NULL 제약 조건**

H2 콘솔에서 제목 없이 게시글을 추가해 본다.

```sql
INSERT INTO board (content, writer)
VALUES ('제목이 없다', '유관순');
```

`NULL not allowed for column "TITLE"`과 비슷한 오류가 발생하며 저장되지 않는다.
DDL에서 `title` 열에 `NOT NULL` 제약 조건을 정의했기 때문이다. **데이터의 규칙은 DDL로 정의한 테이블이 지킨다.**

**4) 정리**

- 테이블은 엔티티로 자동 생성하지 않고, **DDL 스크립트**(`db/schema.sql`)로 직접 정의한다.
- 스프링 부트의 SQL 초기화 기능(`spring.sql.init.*`)으로 애플리케이션이 시작될 때 DDL을 실행한다. `IF NOT EXISTS` 덕분에 여러 번 실행해도 데이터가 유지된다.
- 엔티티는 테이블에 맞춰 작성하고, `ddl-auto=validate`로 엔티티와 테이블이 맞는지 **검사만** 한다.
- `JpaRepository`를 상속한 인터페이스만 선언하면, `save()`, `findAll()`, `findById()`, `count()` 등으로 SQL 없이 데이터를 다룰 수 있다.
- 파일 모드의 H2 데이터베이스는 애플리케이션을 다시 실행해도 데이터가 유지된다.

> 2장에서 Actuator를 추가하고 `show-details=always`를 설정했다면, [http://localhost:8080/actuator/health](http://localhost:8080/actuator/health) 에 `db` 항목이 추가된 것도 확인해 보자. 스타터를 추가하자 자동 구성이 데이터베이스 상태 확인 항목까지 등록했다.
